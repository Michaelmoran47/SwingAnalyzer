# RTMPose backend

Second pose backend behind the `PoseEstimator` interface, via
[rtmlib](https://github.com/Tau-J/rtmlib) and ONNX Runtime. Top-down: YOLOX
person detector, then RTMPose on the best box. Output is COCO-17, the same joint
set as the MediaPipe backend, so nothing downstream changes.

## Install and run

```bash
pip install -e ".[rtmpose]"        # CPU. For an NVIDIA GPU: pip install onnxruntime-gpu instead of onnxruntime
swing overlay data/raw/<clip>.MOV --backend rtmpose --keypoints outputs/<clip>_rtmpose.npz
swing overlay ... --backend rtmpose --device cuda     # on a machine with CUDA
swing overlay ... --backend rtmpose --rtm-mode performance   # larger models: slower
```

On first use rtmlib downloads the ONNX models from `download.openmmlab.com`
(OpenMMLab's official host) into `~/.cache/rtmlib`. `balanced` mode is about
90 MB (YOLOX-m) plus 48 MB (RTMPose-m). The model is chosen with `--rtm-mode`.

When several people are in frame, the subject is the person with the largest
keypoint box weighted by mean score (`select_person`).

## Things to know before using its output

- **Confidence is not comparable with MediaPipe's visibility** and is not a
  reliable error flag. RTMPose scores are SimCC peak values, clipped to [0, 1].
  A `min_conf` chosen for one backend should not be assumed right for the other.
- **It reported confident wrist positions that were wrong** (below).

## Benchmark on the first clip

Full numbers, regenerated by `scripts/benchmark_backends.py`, are in
[benchmark.md](benchmark.md). One clip, one swing, no ground-truth keypoints, so
this compares behaviour and does **not** rank accuracy. Speed was measured on
this machine's CPU (no GPU here); GPU speed is not measured.

What the benchmark shows:

- **Speed (CPU):** MediaPipe about 16 fps, RTMPose about 2 fps at full 1080x1920
  (RTMPose measured 0.41 to 0.51 s/frame across two runs; the timing sample is small).
- **Agreement:** the backends' wrist and hip estimates differ by a median of
  about 0.04 to 0.05 torso lengths in the swing window.
- **Downstream:** with the same code, the two backends give top within 13 ms of
  your label (both), impact within 17 ms (MediaPipe) and 4 ms (RTMPose), and
  similar metric values (for example spine angle at address 35.1 vs 36.4 degrees).
  Address/takeaway/finish are threshold-defined and not scored.
- **Jitter:** RTMPose wrists are steadier in the raw output, its hips less so.

What the benchmark can mislead about:

- **Completeness.** RTMPose is "100% usable" for the wrists in the swing window,
  MediaPipe 84 to 85%. Looking at frames
  (`scripts/compare_frames.py`, e.g. frames 1000-1030 of `IMG_6004`), both
  backends place the wrists on the back and hip, about 1.5 torso lengths from the
  hands that are visibly high near the club, right after impact (motion blur).
  RTMPose reports confidence 0.57 to 0.77 there; MediaPipe's low confidence
  at least flags the problem. So RTMPose's completeness is partly confident
  wrong answers. Checked on six frames by eye; not quantified.

## A bug the second backend exposed

Running RTMPose gave an address frame two frames before the top of the backswing
and an empty tempo. The cause was in `phases/detect.py`, not the backend: hand
speed flickers around the "still" level near the top, and the address scan
treated the first flicker frame as stillness. MediaPipe's trace happened not to
flicker. Fixed by requiring hand speed to rise above `rise_frac` of peak before
stillness counts, with a regression test using noisy synthetic swings (it failed
in 8 of 8 seeds before the fix). MediaPipe results were unchanged by the fix.
The first RTMPose-vs-MediaPipe metric comparison, run before the fix, showed
apparent sign flips in spine change and hip movement; those were caused by this
bug and are not real backend differences.

## Performance mode (larger models)

`--rtm-mode performance` uses YOLOX-x and RTMPose-x at 384x288 (368 MB + 184 MB
download). Run on frames 985-1050 of `IMG_6004` only (the post-impact window):

- **Wrists land on the hands.** By eye on six frames (990, 1000, 1010, 1020,
  1030, 1045, via `scripts/compare_frames.py`), performance-mode wrists sit on
  the golfer's hands where balanced mode and MediaPipe put them on the torso.
  Not quantified against annotations; six frames, one swing.
- **How far apart the two modes are** (`scripts/compare_keypoint_files.py`, torso
  = 344 px): wrists differ by a median of about 1.0 torso length (more than 0.5
  torso apart in 55 and 56 of 65 frames); hips differ by a median of about 0.14
  to 0.17 torso. The hip difference was not examined, so which mode places the
  hips better is unknown.
- **Confidence still does not flag errors.** Performance mode reports 0.96 to
  1.00 on the wrists; balanced mode reported 0.43 to 0.77 on its wrong ones.
  Both are SimCC scores, so a fixed `min_conf` is not a reliable filter for
  either.
- **Cost on this CPU:** about 1.85 s/frame (0.54 fps; 4-frame ad-hoc timing,
  not from the benchmark script), roughly 4x slower than balanced. The whole
  1551-frame clip would take about 48 minutes here. GPU speed is not measured.

Implication: the post-impact wrist failure is a model-capacity problem, not
something smoothing or thresholds can fix. For wrist-based phase detection and
metrics, use performance mode (ideally on a GPU) or add a physical plausibility
check. Whole-clip results for performance mode (phases, metrics) have not been
computed yet.
